# PicUp 上传日志优化设计

## 目标

为 PicUp 的服务启动和图片上传流程提供统一、易读、带本地时间的日志。上传日志需要明确记录生成后的 S3 完整对象路径，并区分开始、成功与失败状态。

## 日志格式

所有应用日志使用 Python 标准库 `logging` 输出，格式统一为：

```text
2026-07-14 15:30:21 | INFO | 开始上传 | object_key=2026/07/1720942221_<uuid>_clipboard.png
```

时间精确到秒，采用进程所在系统的本地时区。日志级别使用标准的 `INFO`、`WARNING` 和 `ERROR`。

## 行为设计

- 在应用级别集中配置日志格式，并让 `app.py` 与 `server.py` 使用命名 logger。
- 服务启动时记录监听地址和 Waitress 线程数。
- S3 对象路径生成后、网络上传开始前，记录“开始上传”和 `object_key`。
- S3 上传成功后，记录“上传成功”、相同的 `object_key` 和耗时毫秒数。
- S3 上传失败时，记录“上传失败”、可用的 `object_key` 和异常原因；凭证缺失和配置不完整同样使用统一日志。
- 将剪贴板读取、水印处理、复制 URL、系统通知以及请求处理中的现有 `print` 错误输出改为对应级别的日志。
- 不在日志中记录 AWS 密钥、访问令牌或图片二进制内容。

## 兼容性与边界

- 保持 `/upload` 和 `/health` 的 HTTP 状态码及响应结构不变。
- 保持 S3 对象路径的生成规则、图片格式、水印行为、剪贴板行为和通知行为不变。
- 应用日志统一输出到标准输出，由现有 launchd 配置写入 `logs/stdout.log`；Waitress 自身写到标准错误的内容仍由 `logs/stderr.log` 收集。
- 不引入新的运行时依赖，也不实现日志轮转或 JSON 日志。

## 错误处理

日志记录不能改变原有容错语义：可恢复的辅助操作失败仍返回 `False` 或原图；S3 上传失败仍返回 `None`，并由上传接口返回现有的失败响应。异常日志使用 `logger.exception` 或等效方式保留堆栈，便于诊断。

## 测试

使用标准库 `unittest` 增加回归测试：

- 验证统一 formatter 输出时间、级别和消息。
- 验证成功上传会依次记录“开始上传”和“上传成功”，且两条日志包含同一个完整 `object_key`。
- 验证上传成功日志包含非负耗时。
- 验证测试通过模拟 S3 客户端完成，不访问真实网络或真实剪贴板。

实现遵循先写失败测试、再补最小实现的测试驱动流程。
