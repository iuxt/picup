# WebP 上传体积优化设计

## 背景

PicUp 当前从 macOS 剪贴板读取图片，按最长边限制缩放并添加水印，随后无条件将结果重新编码为 PNG 上传到 S3。PNG 对照片和复杂截图通常会产生较大的对象，增加上传流量和 S3 存储占用；原图即使已经是 WebP，也会被重新编码为 PNG。

本次优化将上传格式统一调整为 WebP，同时在能够证明图片像素没有变化时，避免重复编码原始 WebP。

## 目标

- 降低上传对象大小、上传流量和 S3 存储占用。
- 新编码图片使用有损 WebP，默认质量为 `82`。
- 原始 WebP 在没有缩放且没有水印时保持字节不变并直接上传。
- 保留现有缩放、水印、S3 目录、HTTP 响应、剪贴板回写和系统通知行为。
- 通过日志记录转换前后的字节数，便于观察实际压缩收益。

## 非目标

- 不同时生成多种格式或响应式图片。
- 不通过两次编码比较有损与无损 WebP 的大小。
- 不根据图片内容自动识别照片或截图。
- 不修改已经存在于 S3 中的 PNG 对象。
- 不为经过处理的动画 WebP 增加逐帧缩放或水印能力；原样直传可以保留动画，发生处理时维持当前只处理 Pillow 当前帧的语义。

## 方案选择

采用“智能直传 + 统一有损 WebP”方案：

- 原始格式为 WebP，且既未缩放也未添加水印时，上传剪贴板提供的原始字节。
- 其他图片统一编码为 WebP，使用 `quality=82`、`method=6`。
- WebP 支持透明通道，编码时保留图片的透明像素。

没有采用以下方案：

- 按透明通道决定有损或无损：透明并不能可靠区分截图和照片，且无损输出可能明显增大。
- 同时编码有损和无损版本再选择较小者：会增加 CPU 时间、延迟和代码复杂度，不符合当前小型本地工具的需求。

## 配置

新增环境变量：

```env
WEBP_QUALITY=82
```

- 默认值为 `82`。
- 允许范围为 `1` 到 `100`，包含边界。
- 非整数或超出范围时在应用启动阶段抛出清晰的配置错误。
- WebP 编码 `method` 固定为 `6`，优先获得较小输出，不新增额外配置。
- `WATERMARK_TEXT` 为空字符串时视为关闭水印；任何非空字符串都视为需要添加水印。

## 数据结构与职责边界

生产代码继续保留在 `app.py`，与当前项目规模和组织方式一致，但拆分出职责明确的辅助逻辑。

### 剪贴板图片

剪贴板读取结果同时包含：

- Pillow 图片对象；
- 剪贴板提供的原始字节；
- Pillow 从原始字节识别出的格式。

使用一个小型值对象表达这三项数据，避免在处理链路中依赖位置不明确的元组。剪贴板类型按 WebP、PNG、TIFF 和其他现有图片类型的顺序尝试。是否属于原始 WebP 以 Pillow 成功解码后的 `format == "WEBP"` 为准，而不只依赖剪贴板类型名称。

macOS 剪贴板不保证保留最初文件的编码格式。如果剪贴板只提供 PNG 或 TIFF，即使用户最初复制的是 WebP，PicUp 也无法恢复原始 WebP 字节，此时按非 WebP 输入重新编码。

### 上传载荷

编码或直传决策产生一个上传载荷，包含：

- 待上传字节；
- 扩展名 `.webp`；
- Content-Type `image/webp`；
- 处理方式 `passthrough` 或 `encoded`，用于日志。

S3 上传函数只负责对象命名、上传和 URL 生成，不再负责图片编码。这样可以单独测试编码决策，也能确保对象扩展名、内容类型和实际字节格式保持一致。

## 处理流程

`/upload` 按以下顺序处理：

1. 从剪贴板读取图片对象、原始字节和原始格式。
2. 超过 `MAX_IMAGE_DIMENSION` 时按现有 Lanczos 逻辑等比例缩小。
3. `WATERMARK_TEXT` 非空时，在最终尺寸上添加水印；为空时跳过绘制。
4. 判断像素是否发生变化：发生缩放或实际添加水印都视为已变化。
5. 原始格式是 WebP 且像素未变化时，直接使用原始字节。
6. 其余情况将处理后的 Pillow 图片编码为 WebP，使用 `quality=WEBP_QUALITY`、`method=6`。
7. 以 `.webp` 文件名和 `image/webp` Content-Type 上传到 S3。
8. 复制 URL、显示通知，并返回现有 PicGo 兼容响应。

新编码的 WebP 在输入含 ICC 色彩配置时保留 ICC 配置，但不复制 EXIF 或 XMP 元数据，以兼顾颜色正确性、文件体积和隐私。原样直传的 WebP 保留其全部原始元数据。

默认 `WATERMARK_TEXT` 为 `PicUp`，因此默认配置会修改所有图片并触发 WebP 编码。只有将 `WATERMARK_TEXT` 设为空，并且图片不需要缩放时，原始 WebP 才会走字节直传路径。

## 对象命名和兼容性

- 年月目录和时间戳、UUID 命名规则保持不变。
- 固定文件名后缀由 `clipboard.png` 调整为 `clipboard.webp`。
- S3 Content-Type 由 `image/png` 调整为 `image/webp`。
- `/upload` 的成功响应结构仍为 `{"success": true, "result": "<url>"}`。
- 现有 PNG URL 和 S3 对象不受影响。
- 新 URL 面向已确认支持 WebP 的现代浏览器和 Markdown 使用场景。

## 日志

编码决策完成后记录一条结构化日志，包含：

- `source_format`；
- `processing=passthrough|encoded`；
- `input_bytes`；
- `output_bytes`；
- `reduction_pct`。

`reduction_pct` 使用 `(input_bytes - output_bytes) / input_bytes * 100` 计算，允许为负数，以真实反映个别图片编码后可能变大的情况。日志不记录原始图片内容或图片字节。

现有 S3 上传开始、成功、耗时和失败日志继续保留，并使用新的 `.webp` 对象路径。

## 错误处理

- 剪贴板中没有可解码图片时，保持现有 `400` 响应。
- 一个剪贴板数据类型解码失败时，继续尝试后续数据类型；全部失败后按无图片处理。
- WebP 编码失败时记录异常并返回现有上传失败语义的 `500` 响应。
- 编码失败时不回退到 PNG，避免对象扩展名、Content-Type 和实际内容不一致，也避免悄悄恢复较大的上传格式。
- S3 配置、凭证和网络错误继续沿用现有错误处理与 HTTP 响应。
- 复制 URL 或显示通知的行为保持现状，不扩大本次变更范围。

## 测试策略

### 配置测试

- 未配置 `WEBP_QUALITY` 时返回 `82`。
- 接受 `1`、`82` 和 `100`。
- 拒绝零、负数、大于 `100` 的整数和非整数。

### 编码测试

- PNG、TIFF 或普通 Pillow 图片编码结果具有有效的 WebP 文件头，并能被 Pillow 重新读取。
- 编码调用使用配置的 `quality` 和固定的 `method=6`。
- RGBA 输入编码后仍具有透明通道和预期透明像素。
- 新编码结果保留可用的 ICC 配置，但不复制 EXIF 或 XMP。

### 直传决策测试

- 原始 WebP、无需缩放且水印关闭时，输出字节与输入字节完全一致。
- 原始 WebP 一旦缩放，必须产生重新编码的字节。
- 原始 WebP 一旦添加水印，必须产生重新编码的字节。
- 非 WebP 即使无需缩放且水印关闭，也必须编码为 WebP。

### 上传与接口测试

- S3 对象键以 `clipboard.webp` 结尾，Content-Type 为 `image/webp`。
- 上传链路顺序为“读取 → 缩放 → 水印 → 编码或直传 → S3”。
- `/upload` 的状态码和 JSON 结构保持不变。
- URL 复制和系统通知继续收到最终 `.webp` URL。
- 现有图片尺寸、上传日志和运行日志测试在更新预期格式后继续通过。

## 验收标准

- 所有新上传对象的扩展名、Content-Type 和实际内容均为 WebP。
- 未发生像素变化的原始 WebP 保持字节完全一致。
- 发生缩放或水印处理的 WebP，以及所有非 WebP 输入，都按质量 `82` 和方法 `6` 编码。
- 透明输入的透明通道得到保留。
- 日志能够显示每次上传的输入大小、输出大小和实际压缩比例。
- 现有尺寸限制、水印位置、S3 路径结构、HTTP 契约、URL 复制和通知行为不发生非预期变化。
